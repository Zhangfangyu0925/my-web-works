DevBoard 总体迭代规划
与一期优化 PRD

以 Issue 为统一需求入口，通过 Issue 内 PRD、开发准备度标签和角色待办，先解决需求不规范、上下文缺失和流程冗余问题，再逐步推进 Task 去重、产品级工作流和 Plan 重构。

版本：V1.0 日期：2026-08-21 一期建议周期：5周 建议方式：按产品灰度
核心建议：Issue 成为唯一需求入口和业务上下文中心；PRD 内嵌 Issue；Task、Spec、Plan 根据需求复杂度按需使用。
01 · 现状判断

为什么需要调整

当前产品模型与真实研发工作方式之间存在明显差异。

需求入口不规范

  • 非 PM 创建的 Issue 经常缺少背景、目标和验收标准。
  • 研发仍需通过会议、群聊或口头方式补齐上下文。
  • Issue 创建门槛低，但进入开发没有明确门禁。

对象和操作重复

  • Issue 与 Task 重复维护标题、描述、负责人和状态。
  • 为了写 PRD 再创建 Issue 或独立文档，会产生新的割裂。
  • 简单需求也可能被迫经过 Plan、Task、Spec。

团队流程不一致

  • 单人团队通常直接通过 Issue 和 Agent 闭环。
  • 常规团队需要 Task，但不一定使用 Plan。
  • 只有高风险、跨团队需求需要完整的 PRD 与 Spec。

角色缺少行动指引

  • PM 不清楚有哪些 Issue 待梳理。
  • 技术负责人缺少待技术判断队列。
  • 研发无法快速判断哪些事项已经可以开发。
02 · 目标模型

一个需求只维护一份业务上下文

简单需求

轻量闭环

Issue → MR → Verify

适合小 Bug、文案样式、单人产品和低风险改动。

标准需求

常规研发

Issue → PRD → Task/MR → Verify

适合大部分常规产品研发，可以按需拆分 Task。

复杂需求

严格流程

Plan → Issue → PRD → Task → Spec → MR

适合跨团队、架构、权限、数据迁移和高风险项目。

对象重新定位

对象重新定位不再承担
Issue需求入口、业务上下文、验收标准和研发链路聚合不只是简单问题描述
PRDIssue 内的结构化需求说明不再创建另一个 PRD Issue
Task复杂需求的执行拆分不重复维护业务背景和验收标准
Spec高风险技术改动的开发门禁不要求所有 Task 都必须有 Spec
Plan多个 Issue 的规划和里程碑聚合不再作为所有开发的必经入口
03 · 总体规划

四阶段完成系统收敛

一期 · P0

Issue 规范化

Issue PRD、准备度标签、待梳理队列、开发门禁。

建议周期：5周
二期 · P1

Task 去重

Task 嵌入 Issue、我的工作、简单需求免 Task。

建议周期：5周
三期 · P1

工作流配置

轻量/标准/严格模式、产品门禁配置、接入向导。

建议周期：6周
四期 · P2

Plan 与运营

产品规划、交付计划、评审闭环和健康度看板。

建议周期：6周
一期

先解决需求能否进入开发

一个不规范 Issue 能够在同一页面被补全、确认，并安全进入开发。

二期

再解决用户在哪里完成工作

研发不再在 Issue、Task、Spec 多个页面之间寻找上下文。

三期

允许产品选择适合自己的流程

产线提供默认规则，产品根据团队规模和风险进行覆盖。

四期

让 Plan 回归规划和运营

以 Issue 落地进度反映规划执行结果，并形成评审和复盘闭环。

04 · 角色体验

每个角色只看到自己下一步要做什么

提交者

  • 我创建的 Issue
  • 待我补充的信息
  • 最近的处理进度
  • 最终交付结果

PM / 产品负责人

  • 待梳理 Issue
  • 待完善 PRD
  • 待产品确认
  • 已可开发但未排期

TL / 技术负责人

  • 待技术确认
  • 待判断 Task / Spec
  • 缺少代码库信息
  • 可开发但无人领取

研发

  • 分配给我的可开发事项
  • 可以自主领取的事项
  • 开发中与阻塞事项
  • MR 待处理和待验证

一期优先通过工作台卡片、预设标签筛选和快捷入口实现，不立即重构全部导航。

05 · 一期 PRD

Issue 规范化与开发准备度优化

一期核心问题

非 PM 创建的 Issue 信息不完整，无法直接进入开发；再创建 PRD Issue、Task 或独立文档又会造成重复。

一期目标：让一个不规范 Issue 在同一页面完成需求补充、PRD 确认和开发条件判断。

一期目标

  • PRD 可以直接在 Issue 内创建和维护。
  • 复用现有 Issue 标签组表达开发准备度。
  • 非 PM 创建的 Issue 自动进入待梳理队列。
  • PM 可以决定是否需要 PRD，并完成产品确认。
  • 技术负责人可以判断 Task、Spec 和开发条件。
  • 简单需求可以直接通过 Issue 关联 MR。
  • 所有确认、流转和豁免行为有审计记录。

一期非目标

  • 不删除 Task 页面
  • 不重构 Plan
  • 不要求历史 Issue 补 PRD
  • 不迁移历史 Plan、Task、Spec
  • 不建设完整工作流引擎
  • 不支持自由表单设计器
  • 不实现复杂多人会签
  • 不一次性修改 Issue 状态体系
06 · 一期功能

在 Issue 内增加 PRD 入口

概览 ｜ PRD ｜ 开发 ｜ 关联内容 ｜ 动态

简版 PRD 内容

  • 背景
  • 问题定义
  • 目标
  • 非目标
  • 核心功能
  • 规则与限制
  • 验收标准

PRD 状态

  • 无需 PRD：简单、明确、低风险改动
  • 草稿：内容仍在整理
  • 待确认：等待产品负责人确认
  • 已确认：可以进入后续技术判断

关键规则

  • PRD 与 Issue 1:1 关联，不产生新的 Issue。
  • 选择“无需 PRD”必须填写原因，并记录操作人和时间。
  • 已确认 PRD 修改后重新进入“待确认”。
  • 一期支持结构化编辑和阅读，不建立独立 PRD 列表。
  • AI 可以生成草稿和缺失问题，但不能自动确认 PRD。
07 · 一期功能

用现有 Issue 标签组承载开发准备度

开发准备度表达需求成熟程度，与 Todo、In Progress、Done 等生命周期状态相互独立。

待梳理尚未经过产品判断，非 PM Issue 默认进入。
待补充缺少场景、证据、预期结果或验收标准。
待产品确认等待确认需求范围、价值和 PRD。
待技术确认等待判断代码库、Task、Spec 和依赖。
可开发上下文与门禁满足，可以领取或进入开发。

默认规则

创建场景默认准备度后续处理
非 PM 创建待梳理进入产品分诊人的待办队列
PM / 产品负责人创建待产品确认补充 PRD 与验收标准后进入技术确认
明确的小型 Bug待梳理分诊人可豁免 PRD，快速推进技术确认
历史 Issue保持现状首次进入开发时提示补充，不强制批量迁移

标签组规则

  • 标签组名称为“开发准备度”，组内单选。
  • 作为系统保护标签组，避免与普通业务标签混用。
  • 普通提交者不能直接标记“可开发”。
  • 列表和详情均支持展示、筛选和授权后的快捷变更。
  • 所有准备度变化写入 Issue 动态和审计记录。
08 · 一期功能

建立轻量开发门禁

一期采用“强提醒 + 授权角色可豁免”，避免直接阻塞现有工作。

触发检查的操作

  • 标记 Issue 为开发中
  • 研发领取 Issue
  • 创建开发 Task
  • 创建开发 MR
  • 调用 Agent 开始开发

默认可开发条件

  • 准备度为“可开发”
  • 有负责人或允许自主领取
  • 验收标准明确
  • PRD 已确认或已豁免
  • 技术判断已经完成

紧急豁免

线上紧急问题允许跳过门禁，但必须选择原因、填写说明、记录操作人，并在问题处理后补充验收与复盘。

09 · 一期功能

产品级 Issue 模板 MVP

产品需求

当前问题、目标用户、使用场景、预期结果、影响范围。

Bug

当前现象、复现步骤、环境版本、期望结果、影响范围。

客户反馈

客户场景、反馈内容、证据附件、影响范围、期望结果。

技术优化

当前技术问题、影响、改进收益、风险和验证方式。

一期配置范围

  • 模板是否启用
  • 字段是否必填
  • 字段提示文案
  • 默认负责人
  • 是否默认要求 PRD
  • 默认开发准备度

11 · 一期验收

一期验收标准

PRD

  • Issue 内可创建、编辑和查看 PRD
  • 不产生新的 PRD Issue
  • 支持草稿、待确认、已确认、无需 PRD
  • 确认和豁免有审计记录

开发准备度

  • 单选标签组正常工作
  • 非 PM Issue 默认待梳理
  • 列表和详情均可筛选展示
  • 标记可开发执行条件检查

角色待办

  • PM 可查看待梳理和待产品确认
  • TL 可查看待技术确认
  • 研发可查看可开发事项
  • 提交者可查看待自己补充

兼容与开发入口

  • 简单 Issue 可直接关联 MR
  • 开发动作触发准备度检查
  • 历史 Issue 和关联数据不丢失
  • 未启用产品保持原有行为
12 · 开发计划

一期建议实施排期

第1周

方案与基础模型

PRD、数据模型、准备度标签、权限流转、交互原型和试点产品确认。

第2周

PRD 能力

PRD 模型与接口、Issue PRD 页签、编辑保存、确认、豁免和审计。

第3周

开发准备度

系统标签组、默认规则、流转校验、列表快捷操作和预设筛选。

第4周

开发门禁与角色入口

Task/MR/Agent 前检查、豁免、角色待办和开发关联聚合。

第5周

联调与灰度

兼容验证、权限验证、试点灰度、数据埋点、文档和反馈收集。

灰度策略

轻量产品

验证 Issue → MR 是否真正降低单人团队使用成本。

标准团队

验证 Issue → PRD → Task/MR 是否减少重复录入。

管理较混乱团队

验证待梳理队列和模板是否提升 Issue 完整率。

13 · 效果评估

一期核心指标

业务指标

  • 非 PM Issue 信息完整率
  • 创建到首次梳理的平均时间
  • 待梳理超过两个工作日的比例
  • 因需求不清被退回的比例
  • 有验收标准的开发中 Issue 比例

体验指标

  • 获取完整上下文的页面跳转次数
  • Issue 到开发的平均操作步骤
  • PM 梳理一个 Issue 的平均耗时
  • 用户对“下一步做什么”的理解度
  • Issue、Task、Plan 重复录入次数
14 · 汇报决策

需要确认的四个方向

  1. 是否认可 Issue 成为唯一需求入口和业务上下文中心。
  2. 是否认可 PRD 内嵌 Issue，而不是创建新的 PRD Issue。
  3. 是否认可 Task、Spec、Plan 根据需求复杂度按需使用。
  4. 是否认可不同产品最终可以配置不同工作流。
一期不推翻现有流程，而是先用最低成本补齐 Issue 的需求质量和进入开发能力；通过产品灰度验证效果，再逐步完成系统去重与工作流重构。
